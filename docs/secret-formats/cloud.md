# Cloud credential formats

See [evidence definitions](README.md#evidence-vocabulary). Checked 2026-10-04.
A credential can be a collection of fields; recognizing one field does not mean
that the entire credential has been found or that it can be authenticated.

| ID | Documented structure | Recognition and disclosure implications | Primary sources |
| --- | --- | --- | --- |
| aws-access-id | `AKIA` long-term access ID; `ASIA` STS temporary access ID. S3 guide describes 20 alphanumeric characters | Identifies the access-ID part, not the secret access key. STS API accepts broader 16..128 length constraints, so distinguish common issued shape from API input validation. | [STS prefixes](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetAccessKeyInfo.html), [request credentials](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/MakingRequests.html) |
| aws-secret-key | Secret access key is described as 40 characters; no distinctive public provider prefix | Context-only. Many unrelated values share that length. Pairing with an access ID supplies context, not proof of validity. Redact the secret field even if its length is wrong. | [Request credentials](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/MakingRequests.html) |
| aws-session-token | STS temporary credentials include a session/security token in addition to access ID and secret | Treat as opaque and contextual; never assume a fixed length or skip it after redacting the other two fields. | [Temporary access IDs](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetAccessKeyInfo.html), [signed request](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html) |
| aws-signed-url | SigV4 query fields include `X-Amz-Credential`, `X-Amz-Signature`, and optional `X-Amz-Security-Token`; credential includes slash-separated scope | A presigned URL is a bearer-like capability. Percent-encoded field values need structural parsing; remove signatures/security tokens and protect access-ID material without erasing unrelated URL context. Never execute the URL to test it. | [Query authentication](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-query-string-auth.html) |
| google-service-account | JSON `type: service_account`, `private_key` PEM, `private_key_id`, `client_email`, and related metadata; REST `privateKeyData` is an encoded key object | `private_key` and private key data are secrets. Key ID, project ID, and client email are metadata rather than the private key. Classification should never dump decoded key content. | [Create/delete keys](https://docs.cloud.google.com/iam/docs/keys-create-delete) |
| azure-storage-key | Semicolon-separated connection fields include `AccountName`, `AccountKey`, service endpoints, and `SharedAccessSignature` | `AccountKey` is contextual secret material. Account name and endpoints identify configuration; their presence alone is not proof of a secret. Parse the dialect instead of treating generic Base64 as an Azure key. | [Connection strings](https://learn.microsoft.com/en-us/azure/storage/common/storage-configure-connection-string) |
| azure-sas | SAS capability is a resource URI with signature and authorization query parameters, including `sig` | Classify from the parameter set and resource context, not a generic `sig` value alone. Redact signature material; preserving permission/expiry context must never expose the bearer capability. | [SAS overview](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview), [SAS connection strings](https://learn.microsoft.com/en-us/azure/storage/common/storage-configure-connection-string) |
| cloudflare-current | Global key `cfk_`, user token `cfut_`, account token `cfat_`, followed by 40 characters and a checksum | Explicit documented structure. The page does not establish the checksum algorithm/length or complete body alphabet; do not invent them. A checksum failure cannot release a candidate. | [Token formats](https://developers.cloudflare.com/fundamentals/api/get-started/token-formats/) |
| cloudflare-legacy | Earlier global keys: 37..45 lowercase hexadecimal characters; user/account tokens: 40 alphanumeric characters | Legacy credentials remain usable. Those shapes overlap ordinary data and require context for provider attribution. Current-prefix-only coverage is incomplete. | [Token formats](https://developers.cloudflare.com/fundamentals/api/get-started/token-formats/) |
| supabase-current | `sb_secret_` and `sb_publishable_`; self-hosting docs describe a 22-character random part, underscore, and eight-character checksum | Secret key is privileged/server-side; publishable key is intended public. These are opaque strings, not JWTs. Self-hosted gateways match opaque strings and do not validate checksums. Do not extrapolate undocumented alphabet/algorithm constraints. | [API key types](https://supabase.com/docs/guides/getting-started/api-keys), [self-hosted key format](https://supabase.com/docs/guides/self-hosting/self-hosted-auth-keys) |
| supabase-legacy | `anon` and `service_role` keys use HS256 JWTs and can coexist with new keys | JWT syntax alone does not identify Supabase or privilege. Decoded role claims are untrusted and must not be printed. `anon` is intended public; service-role credentials are privileged. | [API key types](https://supabase.com/docs/guides/getting-started/api-keys) |

Google/Gemini API keys are covered in [provider formats](providers.md#ai-providers).
Cloud resource IDs, client IDs, and tenant IDs are not automatically credential
secrets. Conversely, a UUID or ordinary-looking string may be a client secret;
context still matters. Avoid generic "all UUIDs are tokens" rules.
